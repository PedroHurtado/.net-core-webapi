Reservations, Menus, Policies...

Futuros microservicios

Cada bounded context del dominio Fudie será un microservicio independiente. Todos consumen el JWT con tenantId + role para operar dentro del contexto del restaurante.

Principios clave

🏢 Restaurant = Tenant

Cada restaurante es un tenant aislado. Solo puede existir uno por suscripción. Se crea automáticamente en el flujo de compra, nunca por el usuario.

🎫 Un solo JWT, tres estados

Siempre un token activo. Con solo userId → selector. Con userId + tenantId + role → dentro del restaurante. Se reemplaza, nunca se apilan.

🔒 Nada expuesto en URLs

El userId, tenantId y role viajan exclusivamente en claims del JWT. Las consultas de memberships son opacas — el backend lee el token, no recibe IDs por ruta.

Flujo de Login
1

Google OAuth

El usuario se autentica con Google. Se obtiene el userId verificado.

2

Consulta Memberships

Auth Service busca memberships por userId en su colección interna. Resultado: lista de {restaurantId, restaurantName, role}.

3

Decisión

1 membership →

JWT directo con userId + tenantId + role. Redirect al dashboard.

N memberships →

JWT solo con userId. Se muestra el selector de tenant.

4

Entra al Restaurante

Con JWT completo (userId + tenantId + role), toda la API del restaurante está disponible.

Flujo de Compra de Suscripción
1

Checkout

El usuario inicia la compra. Se guardan userId + datos fiscales en la colección de suscripciones pendientes.

2

Stripe Webhook → OK

Stripe confirma el pago. El Subscription Service tiene userId y datos fiscales disponibles para orquestar.

3

POST /restaurant

Se crea el restaurante con datos fiscales. JWT del usuario (solo userId). Devuelve restaurantId. Se crea con IsActive = false.

4

Crear Membership

Auth Service registra la membership: userId + restaurantId + role: Owner.

5

JWT Final

Se genera JWT con userId + tenantId + role: Owner. Redirect al dashboard del restaurante.

⚡ El POST /restaurant es el único endpoint que acepta JWT sin tenantId

Es el momento de creación del tenant. A partir de aquí, todo el resto de la API exige JWT completo con tenantId + role.

Cambio de Tenant (sin re-login)
1

Usuario dentro de un restaurante

JWT activo con userId + tenantId: rest-001 + role: Owner. Está revisando reservas.

2

Quiere cambiar de restaurante

En la UI (dropdown, menú lateral) selecciona otro restaurante de su lista.

3

POST /auth/tenant-token

Envía {restaurantId: rest-002}. Auth Service valida que el userId del JWT tiene membership activa en ese restaurante.

4

Nuevo JWT

Se reemplaza el JWT anterior. Ahora: userId + tenantId: rest-002 + role: Manager. Redirect al dashboard del nuevo restaurante.

🔒 Seguridad del cambio

El endpoint /auth/tenant-token valida internamente que el userId tenga membership activa en el restaurantId solicitado. Si alguien intenta fabricar un cambio a un tenant sin membership → rebota.

Estados del JWT
🔑

JWT sin Tenant

Post-login · N memberships

Claims
userId"usr-a1b2c3"
tenantId—
role—

Solo permite acceder al selector de tenant y al POST /restaurant (creación post-compra).

🔑

JWT con Tenant

Dentro del restaurante

Claims
userId"usr-a1b2c3"
tenantId"rest-x7y8z9"
role"Owner"

Acceso completo a la API del restaurante. Todos los endpoints leen tenantId y role del token.

Regla de oro

Siempre un solo JWT activo. Si tiene tenantId + role → estás dentro de un restaurante. Si solo tiene userId → toca elegir tenant. El JWT se reemplaza en cada cambio de contexto, nunca se apilan.
